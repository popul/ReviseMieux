## Phase B bis : Pipeline LLM

### Architecture actuelle

Le code actuel utilise un pattern adaptateur LLM bien concu :
- `llm.AdaptateurLLM` : interface avec 6 methodes (`GenererTexte`, `GenererJSON`, `ExtraireTexteImage`, `DetecterOrientation`, `EstDisponible`, `Nom`)
- `llm.GestionnaireLLM` : fallback automatique primaire -> secondaire
- Implementations : OpenAI (`openai.go`), Mistral (`mistral.go`)
- OCR hybride : Tesseract (positions) + LLM (texte enrichi), fusion intelligente (`ocr/hybride.go`)

### Ecarts avec les specs

1. **Pas de pipeline 2 etages** : les specs prescrivent OCR (vision, Gemini Flash) + IDP (texte, mistral-small) separement. Le code fait tout en 1 passe.
2. **Pas de Gemini** : le benchmark recommandait Gemini Flash pour l'OCR. Le code utilise OpenAI GPT.
3. **Prompts en dur** : les prompts sont des strings Go dans `services/generation.go`, `services/concepts.go`, etc. Les specs prescrivent des fichiers `.txt` avec `go:embed`.
4. **Pas de fidelity check** : aucun controle de fidelite LLM (Z3-AC10 implementee a `e543dea` mais supprimee).

## Phase C : Architecture hexagonale

### Etat a `e543dea`

Architecture hexagonale conforme :
```
domain/ (0 imports externes) --> mastery/, chapter/, session/, validation/, event/
app/ (importe domain/) --> mastery_service, pipeline_service, session_service, validation_service, onboarding_service
infra/ (importe domain/) --> postgres/ (repositories), anthropic/, mistral/, openaicompat/, eventbus/
http/ (importe app/ + domain/) --> handler/, middleware/, dto/, router.go
```

### Etat actuel

Architecture plate :
```
api/ (importe services/ + store/) --> handlers, routes, middleware
services/ (importe llm/ + store/ + ocr/) --> generation, ocr, concepts, lexique, examen, plans, etc.
store/ (importe sql/pq) --> repositories PostgreSQL
llm/ (standalone) --> adaptateur interface + OpenAI + Mistral
ocr/ (standalone) --> hybride Tesseract + LLM
```

**Violations de l'hexagonal :**
- Pas de couche domaine : la logique metier est dans `services/` et `api/handlers*.go`
- Les entites DB (`store.Cours`, `store.Quiz`) sont exposees directement dans les reponses HTTP (pas de DTOs)
- Les interfaces repository sont definies dans `store/` (cote implementeur), pas cote consommateur
- Pas de ports pour les services externes (LLM, OCR)

## Analyse de la divergence

### Chronologie

1. **Mars 2026 (commits `ac4f82d` - `e543dea`)** : Implementation DDD complete en ~20 commits.
   - 5 bounded contexts, 85+ tests TestZ\*AC\*, architecture hexagonale stricte
   - 53/53 ACs implementees avec TDD

2. **Janvier-Fevrier 2026 (commits `f047a63` - `ec69500`)** : Merge avec une branche de dev separee.
   - Commit `f047a63` : "auto-commit before merge (loop primary)" -- agent Ralph
   - 63 commits entre `e543dea` et `ec69500` reecrivent le backend
   - Toute la couche `domain/`, `app/`, `infra/`, `http/` est supprimee (-12,674 lignes)
   - Remplacee par une architecture `api/services/store/llm/ocr`

3. **Fevrier 2026 (commits `ec69500` - `86316a0`)** : Ajout de features sur la nouvelle architecture.
   - Concepts, lexique, examens blancs, plans de revision
   - Frontend TypeScript complete
   - Tests e2e Playwright

### Cause probable

Deux flux de travail paralleles ont ete merges sans reconciliation :
- **Flux DDD** : implementation methodique des specs Lot 0 avec TDD
- **Flux pragmatique** : prototype fonctionnel avec OCR, generation LLM, frontend web

Le merge a ecrase le flux DDD au profit du flux pragmatique.
